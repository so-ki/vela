# ADR：垂直优先，平台从参考包里提炼

- 日期：2026-07-18
- 状态：已接受（accepted）
- 关联：`docs/design/平台骨架v0.1与参考能力包v0.1.md`、`docs/design/CODE_REVIEW_CHECKLIST.md`、`docs/experiments/README.md`

## 背景

围绕"先搭平台骨架，还是先做深巴西垂直场景"，前后讨论了九轮。争论的实质不是要不要平台——双方都同意最终形态是"法域中立机制层 + 可插拔能力包"——而是**抽象发生在什么时刻**：是在只有一个法域样本时预先设计通用结构，还是先把一个法域做扎实、等第二个法域出现时再从重复中提炼。

本仓库现状放大了这个问题：巴西内容（语料、规则、门户、葡语字段、默认值）散布在核心代码各处，README 明写"以巴西法域做深后再扩展"。任何平台化动作都必须回答：抽象的依据是什么？

## 决定

**垂直优先。平台不是设计出来的，是从参考能力包里提炼出来的。**

本次落地范围（刻意薄）：

1. **薄骨架**：manifest（`backend/app/packs/brazil_new_energy/manifest.json`，v0.1-draft）+ 薄加载器（读配置文件，无注册机制）+ 五个机制件——六态材料账本、事实五元组、Claim 编译器、覆盖证明、拒答门（数据模型已落 `backend/app/models/`，枚举已落 `backend/app/core/statuses.py`，服务层按蓝图推进）。机制层只编码认识论纪律，不编码法律内容。
2. **参考包数据归位**：巴西的规则卡 schema、语料、门户、house rules 全部经 manifest 引用，manifest 成为唯一入口；核心代码中的巴西硬编码按蓝图清单逐步迁出。

不做的部分见设计说明 §5（无规则 DSL、无注册机制、无签核工作流、无认证状态机、无第二法域内容）。

## 后果

- **接受重复**。包内结构与未来的平台抽象会有重叠，第二个包立项前不做去重。重复是提炼的原料，不是债务。
- **容忍 provisional**。全部规则卡未经巴西执业者核验，`certification_status` 现阶段恒为 provisional，对外表述如实（招募与核验见 `docs/recruitment/巴西法学生招募帖.md`）。
- **第二个能力包立项日 = 提炼日**。manifest 与规则卡 schema 的破坏性变更窗口开到那天为止；立项当天的第一项工作就是对照两个包提炼共性、冻结 v1 结构。
- **巴西恰是离群值，不得写成平台公理**。LexML URN 体系、`legislationChanges` 修订关系、法条文本不受版权保护——这些都是巴西特产，别的法域未必有对应物。实验①的实测结果甚至表明 LexML SRU 对首包 30 条目标法规的元数据覆盖率为 0%（`docs/experiments/results/exp01_result.md`）：以巴西经验做全称判断，连巴西自己都会证伪它。已知渗漏样本一例：`backend/app/packs/rule_card.schema.json` 的 `^urn:lex:br` pattern 写在平台级 schema 里，已记录在案，提炼日下放为包级约束。

## 替代方案与否决理由

**方案 B：骨架先行**——先设计通用 manifest/规则模型/多法域接口，再把巴西内容装进去。否决，理由三条：

1. **无独立完工标准**。只有一个法域时，骨架"做完了没有"无法判定——没有第二个样本做检验，验收标准只能来自想象中的需求，做多做少都论证不了。
2. **信息时序错**。区分共性与特性所需的信息，只有做完第二个包才会出现。骨架先行等于在信息最少的时刻做约束力最强的决定，之后每个包都要迁就当初的猜测。
3. **错误代价不对称**。把包内容错放进平台（该下放）要动核心接口和所有调用方；把平台内容错放进包（该上提）只需在第二包出现重复时做一次局部上提。骨架先行会系统性制造第一类错误；垂直优先把错误集中在便宜的那一侧。这条不对称性同时是"拿不准默认放包"纪律的依据。
