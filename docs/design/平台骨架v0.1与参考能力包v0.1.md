# 平台骨架 v0.1 与参考能力包 v0.1（设计说明）

> **定位一句话**：本次交付是**平台骨架 v0.1 ＋ 参考能力包 v0.1（brazil_new_energy，外部代号 br-sp-new-energy）**，不是"巴西场景 v1.0"。巴西·圣保罗·新能源包是用来提炼平台的参考实现；平台本体只包含法域中立的机制件。
>
> 决策依据见 `docs/decisions/2026-07-18-vertical-first-platform-abstraction.md`。

---

## 1. 核心纪律（三条）

### 1.1 删除巴西测试

平台是否中立的唯一操作性判据：**删掉全部巴西语料和规则后，平台仍能启动、仍能对任何提问给出正确的结构化拒答**（`pack_not_installed`），而不是崩溃、空答或静默回退到硬编码的巴西默认值。

归属判定推论：删掉巴西内容后，**"不知道该查什么"的东西属于包**——查什么、怎么措辞、哪个门户、哪些红旗，都是知识；**"不知道怎么记账、怎么拒答"的东西属于平台**——账本怎么记、证据怎么挂、拒答怎么给理由，是机制。

### 1.2 拿不准默认放包

上提便宜，下放昂贵：

- 包里的东西日后发现是共性 → 第二个包出现重复时上提，一次局部重构；
- 平台里的东西日后发现是巴西特性 → 下放要动核心接口和全部调用方，且此前所有依赖它的代码都被污染。

因此归属存疑时**一律先放包**。没有"先放平台，以后再说"。

### 1.3 manifest v0.1-draft 结构显式标软

`backend/app/packs/brazil_new_energy/manifest.json` 首行 `_notice` 与 `backend/app/packs/rule_card.schema.json` 的标题都写明：**第二个能力包立项前允许破坏性变更**。在那之前：不为 manifest 结构做兼容层、不写结构迁移脚本、不对外承诺字段稳定。立项日即冻结日（见 ADR）。

## 2. 机制层 / 知识层 / 危险带

### 2.1 机制层（平台骨架）

六个机制件：**六态材料账本、事实五元组、Claim 编译器、覆盖证明、拒答门、审计日志**。

它们编码的是**认识论纪律**，不编码法律内容：

| 机制件 | 回答的问题 | 落位 |
|---|---|---|
| 六态材料账本 | 每份材料处理到哪一步了？ | `backend/app/models/material_ledger.py` + `backend/app/services/material_ledger_service.py` |
| 事实五元组 | 每条事实的出处是哪个材料块？ | `backend/app/models/fact.py` + `backend/app/services/fact_service.py` |
| Claim 编译器 | 每条对外结论背后挂着什么证据？ | `backend/app/models/claim.py` + `backend/app/services/claim_compiler.py` |
| 覆盖证明 | 该查的查完没有？分母是谁定的？ | `backend/app/models/coverage.py`（聚合服务按蓝图落 `services/coverage_service.py`） |
| 拒答门 | 答不了时能否明说、说清原因类别？ | `backend/app/core/statuses.py` 的 `AnswerabilityReason`（门服务按蓝图落 `services/answerability_gate.py`） |
| 审计日志 | 谁在何时做了什么？ | `backend/app/services/audit.py`（已有） |

（表内个别服务文件仍在按蓝图落地中，以仓库现状为准；落位路径即验收路径。）

机制层不知道 CLT 是什么、不知道 CETESB 发几种许可——它只知道"事实要有出处""结论要有证据""穷举要有官方分母"。70 分门控与 S1/S2/S3 分级的权威口径仍以 `docs/match_tier_and_gate.md` 为准，拒答门是叠加而非替换。

### 2.2 知识层（能力包）

规则卡、法源语料、术语/关键词、红旗、输出配置（双语文案、门户链接、boilerplate 短语），**整个活在包里**——即包目录 `backend/app/packs/brazil_new_energy/` 与其 manifest `components` 所引用的数据文件（现阶段仍指向历史位置 `backend/app/rules/brazil_new_energy.json`、`backend/app/data/brazil_legal_corpus.json` 等，属过渡态，manifest 是唯一引用入口）。

### 2.3 危险带

危险带 = **从巴西悄悄渗进机制层的结构性假设**。它比显式的巴西字面量更危险，因为看起来像"合理的平台设计"。已识别的例子：

- **"法源必有 URN"**——URN 是 LexML 体系的特产。实验①首轮还发现 LexML 的程序化访问本身被塞纳多反爬体系封锁（对云端出口 30/30 查询返回挑战页，覆盖率**未知而非 0%**，判定为仪器失效，见 `docs/experiments/results/exp01_result.md`）：连"URN 元数据随时可查"这个前提都依赖出口网络环境，更不配当平台公理。
- **"许可必是三段式"**——LP/LI/LO 三段许可是巴西环境许可制度的特产，不是"许可"这个概念的属性。
- **"法条文本无版权"**——官方文本不受著作权保护是巴西法的特产，换一个法域语料的存储与展示策略可能整个不同。

三条纪律（§1）都是对着危险带设的。**已知渗漏样本（记录在案，第二包立项前处理）**：`backend/app/packs/rule_card.schema.json` 中 `legal_sources.urn` 的 pattern `^urn:lex:br` 写在了平台级 schema 文件里——按纪律 1.2 这条约束属于包，提炼通用 schema 时必须下放为包级 overlay。

## 3. 五个数据对象（最小字段说明）

字段名取自仓库内真实文件，不是设想值。

### 3.1 LegalSourceRecord（语料条目）

来源：`backend/app/data/brazil_legal_corpus.json` 的 `sources[]`（70 条，v1.9）。

| 字段 | 说明 |
|---|---|
| `id` / `source` | 条目标识 / 来源系统（lexml、planalto 等） |
| `urn` / `url` | 法源定位符与外链 |
| `title_pt` / `title_zh` | 双语标题 |
| `dimension` / `level` / `validity` | 审查维度 / 法源层级（federal 等）/ 效力状态（vigente） |
| `published_at` / `lexml_synced_at` | 颁布日期 / 同步时间戳 |
| `tags` / `checklist_codes` | 检索关键词 / 关联清单编号 |
| `text_pt` / `text_pt_clean` / `text_pt_raw` / `text_zh` | 原文（清洗前后）与中文摘要 |

注意：`urn`、`*_pt`、`lexml_synced_at` 这些**字段名本身就是巴西/葡语痕迹**，属知识层；机制层引用语料只能经 manifest 解析，不得直连字段名。蓝图要求补 `content_hash`（sha256）+ `fetched_at` 以支撑 CoverageProof 引用固定语料版本（规划，未落地）。

### 3.2 材料账本条目（MaterialBlock / MaterialBlockTransition）

来源：`backend/app/models/material_ledger.py`（已建表）。

- `MaterialBlock`：`block_uid`、`scenario_id`、`kind`（file / field_set / extract_snapshot）、`filename` / `stored_name`、`content_hash`、`state`（六态，见 §4.1）、`pack_id`、`superseded_by_id`、`created_at` / `updated_at`。
- `MaterialBlockTransition`：`block_id`、`from_state`、`to_state`、`actor_user_id`、`reason`、`created_at`——谁、何时、为何把块从 A 态推到 B 态。

### 3.3 规则卡

来源：`backend/app/packs/rule_card.schema.json`（v0.1 draft）。

必填：`rule_id`、`pack_id`、`version`、`title_zh`、`legal_sources[]`（`urn` + `article` + 可选 `label`）、`elements[]`（`element_id` + `description_zh` + `fact_fields[]`，其中 `fact_fields` 对应事实五元组的 `attribute`）、`consequences[]`、`certification_status`（provisional / reviewed / certified，现阶段全库恒为 provisional）、`production_tracks`（`forward_done` / `reverse_done` / `divergence_types`，对应实验③双轨记录 `docs/experiments/实验③_双轨规则卡工时记录.md`）。

可选：`title_pt`、`exceptions[]`、`red_flags[]`（`flag_id` + `condition_zh` + `severity`）、`checklist_codes[]`（接现有清单/检索流）、`notes`。

### 3.4 事实条目（FactRecord）

来源：`backend/app/models/fact.py`（已建表）。

五元组本体：**`subject`（主体）+ `attribute`（属性）+ `value`（值）+ `asserted_at`（时间）+ `source_block_id`（出处材料块）**。

护栏字段：`source_snippet`、`grounding_score`、`verification_status`、`extraction_method`（rules / llm）、`business_confirmation`（pending / confirmed / disputed）、`fact_pack_version`、`superseded_by_id`。纪律：没有 `source_block_id` 的事实不得支撑 Claim。

### 3.5 覆盖任务（CoverageTask / CoverageProof）

来源：`backend/app/models/coverage.py`（已建表）。

- `CoverageTask`：`scenario_id`、`dimension`、`element_id`、`checklist_code`、`kind`（material_gap / retrieval_gap / element_gap）、`status`（见 §4.2）、`origin`（gate_a / adequacy / zero_hit / red_team）、`denominator_source`、`note`。
- `CoverageProof`：`denominator_source`、`denominator_count`、`covered_count`、`open_count`、`evidence`（claim_ids / fact_ids / task_ids / corpus_version）、`proof_hash`、`generated_at`。

**分母纪律（两种分母，各管一事，均不允许"检索到多少算多少"）**：

| 用途 | 分母来源 | 实现 |
|---|---|---|
| 场景级覆盖证明（该查的要件查了多少） | 包规则声明的**要件全集**（`dimension_elements`，`denominator_source="pack_dimension_elements"`） | `coverage_service.build_scenario_proof`；无包声明要件时**不生成证明**（宁缺毋滥） |
| 来源级穷举声明（`enumerated_absent`，目录穷举后未见） | manifest `coverage_denominators` 声明的**官方法源清单** | `coverage_service.upsert_task` 强制 `denominator_source` 非空，否则抛 `DenominatorRequiredError` |

## 4. 状态机

### 4.1 材料块六态（蓝图 §2，实现于 `backend/app/core/statuses.py`）

六个生命周期阶段；验证阶段有 verified / unverified 两个互斥出口。

| 状态 | 含义 | 主要去向 |
|---|---|---|
| `raw_archived` | 已归档，未抽取 | extracted |
| `extracted` | 已抽取，事实未验证 | verified / unverified / in_use |
| `verified` | 抽取事实全部通过 grounding 验证 | in_use |
| `unverified` | 抽取完成但存在未验证事实 | verified / in_use（须标注） |
| `in_use` | 已被协查包/简报消费 | returned / superseded |
| `returned` | 法务打回待补充 | superseded / extracted（重抽） |
| `superseded` | 已被新版本材料取代 | 终态 |

合法转移以 `backend/app/core/statuses.py` 的 `MATERIAL_TRANSITIONS` 显式转移表为准；非法转移抛错，不静默。

### 4.2 覆盖任务状态

`open` → `satisfied` / `enumerated_absent` / `waived` / `unanswerable`：

| 状态 | 含义 |
|---|---|
| `open` | 该查而尚未闭环 |
| `satisfied` | 已有证据闭环 |
| `enumerated_absent` | **目录穷举后未见**——仅对 manifest `coverage_denominators` 声明了官方分母的来源开放；没有官方分母的来源不得宣称穷举 |
| `waived` | 人工豁免（须记录理由） |
| `unanswerable` | 明确不可答，进拒答链路 |

首包声明的三个官方分母（`sp_state_env_core` / `conama_target` / `federal_target`）均指向实验①的预登记清单，见 `backend/app/packs/brazil_new_energy/manifest.json` 与 `docs/experiments/README.md`。

## 5. 明确不做清单

| 不做 | 边界说明 |
|---|---|
| 通用规则 DSL | 规则卡是数据不是语言；判定逻辑留在服务层代码里 |
| 包加载注册机制 | 加载器=读配置文件（manifest → 资源路径），不做插件发现、entry_points、热加载 |
| 签核工作流 | 不做审批流、不做电子签名、不做核验任务派发 |
| 认证状态机 | `certification_status` 一个枚举字段就是全部；从 provisional 到 certified 靠人（见 `docs/recruitment/巴西法学生招募帖.md`），不靠代码 |
| 任何第二法域内容 | 一行都不写；第二法域是提炼平台的触发器，不是现在的工作 |

## 6. 变更冻结规则

本设计的变更只接受两种触发器：

1. **实验结果**——且仅限 `docs/experiments/README.md` 预登记判据的裁决（判据先行，防事后合理化）；
2. **赛事要求**。

其余动机——"顺手重构""更优雅的抽象""反正要改不如现在改"——一律不作为变更理由。manifest 与规则卡 schema 的破坏性变更窗口随第二个能力包立项日关闭。
