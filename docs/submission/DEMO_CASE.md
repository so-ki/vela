# Aurora 储能系统集成工厂——巴西圣保罗州新能源绿地设厂协查测试案例

星瀚杯复赛最终提交版 · `SYNTHETIC DEMO`  
产品：Vela 面向中国企业法务的拉美投资前合规协查过程保证平台

> 本案例中的企业、业务参数、文件、人员和操作记录均为虚构测试数据，不包含真实客户数据，不构成正式法律意见。当前法律内容均为 `provisional`；律师认证、客户 UAT、客户生产部署和正式 Release 均为 `blocked_external`。

## 1. 测试目标与能力边界

当前完成端到端验证的首个 Capability Pack 为“巴西 · 圣保罗州 · 新能源制造 · 绿地设厂”，环境许可是当前研究最深入的维度。本案例验证：

1. 同一产品在 `5180` 端口按登录角色分流，业务与法务职责清楚。
2. 业务材料、事实确认、补件、法务研究、Claim、CoverageProof、Gate 和审计记录可追溯。
3. Pack 固定调查分母为 30 个调查清单事项，Scope 不隐藏未覆盖项。
4. 事实或证据不足时系统显示拒绝或受限状态，不自动出具正式法律意见。
5. 外部批准证据缺失时交付状态保持 `blocked_external`。

本案例不验证完整拉美、全巴西、市级规则或实时完整更新，不构成律师认证、客户 UAT、客户生产部署或正式 Release 的证据。

## 3. 测试输入

### 3.1 基础材料

文件：`AURORA_BASE_MATERIAL.txt`

基础材料包含项目概况、投资结构、规模、用工、设施与时间线，同时明确以下三项仍需业务补充：

- 最终场址或选址状态
- 危险品最大库存
- 主要生产设备及活动分类

### 3.2 补充事实单

文件：`AURORA_SUPPLEMENT_FACT.txt`

补充事实单由业务账号上传，逐项回应上述三项信息。内容只描述虚构业务事实，不包含法律适用判断或合规结论。

## TC-01｜同端口角色分流

**目的**：验证两个角色使用同一产品和同一前端端口。  
**步骤**：启动比赛环境；先后使用业务与法务账号登录 `http://127.0.0.1:5180`。  
**预期**：业务自动进入 `/competition/1/business`；法务自动进入 `/competition/1/overview`。不需要第二套系统、第二个端口或手工拼接路径。

## TC-02｜业务查看、确认与补件

**目的**：验证业务角色只处理项目材料、业务事实和补件。  
**步骤**：

1. 登录 `biz@demo.vela`，查看 Aurora 项目材料。
2. 确认或更正一项业务事实。
3. 查看三项待补充信息。
4. 上传 `AURORA_SUPPLEMENT_FACT.txt`。
5. 点击“提交法务”。

**预期**：界面显示“已补充，等待法务复核”；三项补件与输入文件一致；业务端不要求理解 ResearchItem、Claim、CoverageProof、法律研究、法源匹配分数或交付 Gate 内部结构。

## TC-03｜法务八页工作台

**目的**：验证法务对法律研究和结论负责。  
**步骤**：退出业务账号，登录 `legal@demo.vela`，依次查看：项目总览、材料与事实、固定 30 项、法律研究、Claim 与缺口、CoverageProof、交付中心、审计记录。  
**预期**：八页均属于同一 Aurora 法务工作台；正式结果来自真实 API；所有法律内容标注为 `provisional`。

## TC-04｜Pack 固定调查分母

**目的**：验证 Scope 不改变调查分母。  
**步骤**：进入“固定 30 项”，核对 Pack 总数、Scope 内项目和 out-of-scope 项目。  
**预期**：分母保持 30 个调查清单事项；页面不把它表述为 30 张规则卡或 30 条法律结论；未覆盖项不会因 Scope 选择而消失。

## TC-05｜研究、Claim 与缺口

**目的**：验证过程对象分层和法务责任边界。  
**步骤**：查看“法律研究”和“Claim 与缺口”。  
**预期**：ResearchItem 与 Claim 分开呈现；Claim 来自法务研究与草稿；事实或证据不足时缺口仍被保留；系统不自动出具正式法律意见；法律内容状态为 `provisional`。

## TC-06｜CoverageProof 0.2 与 Gate

**目的**：验证固定分母、处置计数和拒绝机制。  
**步骤**：查看 CoverageProof 与 Gate 状态。  
**预期**：可见 `schema_version=0.2` 与 `pack_total=30`；Scope 内处置加 out-of-scope 计数可核对；事实或证据不足时 Gate 显示拒绝或受限状态。CoverageProof 证明过程与计数可复核，不证明法律判断正确。

## TC-07｜外部交付边界

**目的**：验证工程结果不能越过真实外部批准。  
**步骤**：进入“交付中心”。  
**预期**：律师认证、客户 UAT、客户生产部署和正式 Release 均为 `blocked_external`；不得解释为系统失败，也不得以虚构证据解除阻断。

## TC-08｜审计可追溯

**目的**：验证操作、对象、版本和状态变化留痕。  
**步骤**：进入“审计记录”，检查材料上传、事实确认、业务提交、法律研究、Claim、CoverageProof、Gate 与交付状态相关事件。  
**预期**：事件来自真实 API；可见操作者、时间、对象与状态；不出现 RC0 或静态拟制事件冒充正式结果。

## 4. 通过标准

TC-01 至 TC-08 全部满足预期；两条角色路径正确；业务补件与三项缺口一致；固定 30 项含义准确；法律内容为 `provisional`；四类外部环节均为 `blocked_external`；没有把虚构案例表述为真实客户项目。
